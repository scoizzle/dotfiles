# Memory and dreaming

Durable memory for this opencode setup, plus an out-of-band pass that turns recent sessions into constraints. The review gates in `AGENTS.md` stay as they are.

## Talk mapping

Lamis Mukta’s “Learning while you Sleep: Beyond Memory to Dreaming” is the source for this layout. The pieces that landed here:

- **Bookshelf.** `memory/INDEX.md` has a one- or two-sentence blurb per file. Agents read the index first and open a file only when the blurb matches the task.
- **Tiers of permission.** `memory/core/` is read-only for agents (conventions and safety). `memory/learnings/` is append-only durable memory. Session transcripts stay in the opencode session store; they are not copied into git.
- **Versioned writes.** Each learnings append starts with who, when (UTC), a session or context id, and a source. `memory/learnings/README.md` is the format.
- **Optimistic concurrency.** `bin/dream` hashes the day’s learnings file before drafting and refuses the append if the file changes twice before the write.
- **Dreaming.** Lessons are written off to the side, after the task, so the task itself is not also a memory edit.

Lessons are constraints, not transcripts. A line is `never:` (dead approach), `known:` (durable fact), or `derived:` (a rule that should change how the next piece of work is cut). The bracket tag says which layer owns it: `harness`, `loop`, or `graph`.

## Where this sits on the ladder

Harness notes often stack the work in levels: memory, then loops and gates, then a learning pass that feeds the next cut. This change is Level 2 memory and Level 7 learning. Loops and gates already live in `AGENTS.md` (tiers, review, the fix cap).

A failure paid for inside a session is written down as a constraint. The next session can load it from the bookshelf, so the same class of failure does not cost a second full pass.

## Layout

| path | role |
| --- | --- |
| `memory/INDEX.md` | bookshelf: the ladder, the taxonomy, and a blurb per file |
| `memory/core/` | curated workflow invariants, edit-denied, portable |
| `memory/learnings/README.md` | append format |
| `memory/learnings/pending/YYYY-MM-DD.md` | staged by dream, unreviewed, not read by agents; tracked only on `memory/dream` |
| `memory/learnings/YYYY-MM-DD.md` | promoted lessons, the archive, tracked |
| `memory/learnings/working.md` | generated by `--promote` from the archive, read first by agents, local |
| `~/.config/opencode/.memory` | the working copy: a sparse clone of this repo, provisioned by `./install.cs` |
| `~/.config/opencode/memory` | symlink to `.memory/memory`: the path consumers already read |
| `~/.config/opencode/bin/dream` | the out-of-band pass |
| `~/.config/opencode/bin/memory-nightly` | dreams, then publishes staged lines to `memory/dream` as a draft PR |
| `commands/dream.md` | `/dream`, which points at that script |

## Working copy

`~/.config/opencode/.memory` is a git clone of this repository, sparse to
`memory/` plus `.gitignore`. `~/.config/opencode/memory` is a symlink to
`.memory/memory`, so every path a consumer already used — `memory/INDEX.md`,
`memory/core/`, `memory/learnings/` — keeps resolving. The clone is not the
checkout you edit.

`./install.cs` provisions it: clone beside `.memory`, set the sparse set to
`/memory/` and `/.gitignore`, then move it in and link `memory` to
`.memory/memory`. Re-running is idempotent, and a failed clone never costs the
existing memory its place. An existing `memory` directory or symlink is moved to
`~/.config/opencode.bak-<stamp>/`; `learnings/**` are copied into the clone
without overwriting, and a differing local file is kept under
`learnings/.conflict/`. An interrupted migration resumes on the next run.
`./install.cs --check` compares the clone's `origin` URL, its sparse set, and its
required files and link, with no network. `--copy` changes the other managed
entries only; memory is the same clone and symlink in both modes.

Dated `memory/learnings/YYYY-MM-DD.md` files are tracked, so they travel with git.
`pending/` is ignored and force-added only on a `memory/dream` branch, and CI
exempts it only there and only while the pull request is a draft; every other ref,
including `main` after a merge, fails on tracked pending. `working.md` is ignored
and rebuilt by `dream --promote` in each working copy.

`opencode.json` denies `edit` on `memory/core/` (edit, write, and patch). Shell text is matched as a command, not as a path, so `AGENTS.md` is what forbids a redirection into core.

## Sources

T3 launches work that never appears in the opencode store: its native `grok` and `claudeAgent` threads. `bin/dream` reads two stores.

| source | covers |
| --- | --- |
| `opencode.db` | every OpenCode session, including T3 `opencode` threads |
| T3 `statev2.sqlite`, `provider in (grok, claudeAgent)` | the threads no other store records |

The modes are `auto` (default), `t3`, and `opencode`. `auto` reads `opencode.db` plus the T3 `grok` and `claudeAgent` threads, and skips a T3 `opencode` thread only when its native session is already in that read of `opencode.db`. The binding is `payload_json.nativeThreadRef.nativeId` on the T3 thread. Turn items are joined on `provider_thread_id`, not `thread_id`, because two provider rows can share one orchestration thread. `--source t3` reads only the T3 projection, all providers; `--source opencode` is the previous behavior.

The T3 tables are `orchestration_v2_projection_*`: internal, derived, and subject to migration. Dream probes their shape and falls back to opencode-only in `auto`; in `t3` mode a missing or unrecognised store is an error. `statev2.sqlite` is live, so the read is read-only with a busy timeout.

Each run prints a coverage line to stderr:

```text
dream: sources opencode=12 t3=3 (grok=2 claudeAgent=1) t3-opencode-skipped=4 unbound-opencode=0
```

`unbound-opencode` counts opencode sessions in the window with no T3 thread. When T3 is the only launcher it should stay at zero; that is the signal to switch the cron job to `--source t3`. Both stores are per machine, so a linked environment needs its own run.

## Run dream

From a machine that has run `./install.cs`:

```sh
~/.config/opencode/bin/dream
~/.config/opencode/bin/dream --dry-run
~/.config/opencode/bin/dream --since 48h
~/.config/opencode/bin/dream --since 2026-10-30
~/.config/opencode/bin/dream --sessions 10
~/.config/opencode/bin/dream --source t3
```

`--since` defaults to `24h` (`Nh`, `Nd`, `Nm`, or an ISO date interpreted as UTC). `--sessions` caps how many sessions in that window are read (default 50). `--db` overrides the opencode store, `--t3-db` the T3 store, and `--source` picks the modes above. `--dry-run` prints the proposed append and does not write.

The session store is the one `evals/scoreboard.py` opens: `~/.local/share/opencode/opencode.db`, table `session_v2`, messages in `session_message`. The T3 store defaults to `~/.t3/userdata/statev2.sqlite`. A missing store prints that path and appends nothing. It is an empty machine, not a crash.

When there is something to learn, dream drafts with the local `opencode` login. The invocation is:

```sh
opencode run --standalone --format json --agent dream-drafter -m opencode-go/deepseek-v4.1-flash <prompt>
```

`dream-drafter` denies every tool and there is no `--auto`, because the digest quotes tool output and error text that a third party may have written. Before the prompt leaves the machine the digest is redacted for credential shapes and framed as untrusted data; every returned line is length-limited and checked for URLs, fetch-and-run, and injection phrasing. See `docs/security-model.md`.

### Staging and promotion

Dream never writes the files agents read. It stages the block in `memory/learnings/pending/YYYY-MM-DD.md`:

```sh
~/.config/opencode/bin/dream --promote --dry-run   # show what is pending
~/.config/opencode/bin/dream --promote             # show, ask, then append to learnings/YYYY-MM-DD.md
```

`--promote` re-validates every line (so an edited pending file cannot smuggle one in), asks on a terminal, and refuses without `--yes` when there is no terminal. A nightly job therefore leaves a review queue, not new instructions.

After the appends, `--promote` compacts: it rewrites only `learnings/working.md` from the dated archive, deterministically (no model, no session-store read). Exact duplicates collapse with their sources cited; same body under a different kind or layer stays separate; a `never` retry line and an affirming retry line that share a token both stay, with a `kept distinct:` note. The dated files are never rewritten or deleted, and `memory/core/` is never written. `--promote --dry-run` prints the working set it would write, including when nothing is pending, and writes nothing. With nothing pending, `--promote` also says whether the working set is stale, and `--promote --yes` rebuilds it only when its digest differs from the archive's.

To fix a line, edit the dated file, then run `dream --promote --yes`. The nightly job runs `dream` through `memory-nightly`, never `--promote`, so `working.md` changes only when a person promotes.

The model is pinned so a change to the top-level `opencode.json` model cannot move this nightly job onto Claude quota. `--model` or `DREAM_MODEL` overrides it. The prompt is fixed in `bin/dream`. It asks for markdown constraint lines in the learnings format and tells the model not to edit files. The script does not read API keys. If `opencode` is not on `PATH`, dream exits with a short hint and writes nothing. Run a scheduled job only after `opencode` is installed and logged in on that machine.

## Nightly staging and the draft PR

`bin/memory-nightly` is the scheduled entry point. It runs `dream`, then publishes
the clone's `memory/learnings` state as one commit on `memory/dream` and creates or
reuses a single **draft** PR against `main`:

```sh
~/.config/opencode/bin/memory-nightly
~/.config/opencode/bin/memory-nightly --dry-run     # print the commands, change nothing
~/.config/opencode/bin/memory-nightly --skip-dream  # publish what is already staged
~/.config/opencode/bin/memory-nightly --no-pr       # push the branch, skip gh
```

`--repo`, `--branch`, `--base`, `--remote`, and `--dream` override the defaults
(`~/.config/opencode/.memory`, `memory/dream`, `main`, `origin`, and the installed
`dream`). `--repo` accepts the clone root or the `memory` symlink into it; it
resolves the clone root itself. It refuses a repo that is not a work tree or not
sparse to `/memory/`.

What it publishes is an allowlist: dated `YYYY-MM-DD.md` files and
`pending/YYYY-MM-DD.md`. `memory/learnings/README.md` and `.gitkeep` are never
published. A dated file is published only as an append to the upstream copy;
otherwise it is skipped with a warning, so a machine never overwrites another
branch's date. A pending file is removed from the branch only when its dated
counterpart exists locally — the promote signal. `working.md`, the lock, and temp
files are never staged.

A missing or broken `--dream` blocks publishing with one `Fatal` line and pushes
nothing, because the nightly loads dream to validate pending files.

The branch commit is built with plumbing against a temporary index (`read-tree`,
`add`, `write-tree`, `commit-tree`), so the clone's worktree is never switched or
reset; when the resulting tree matches the base tree it commits nothing. It is
fast-forwarded to `origin/main` only when `git status --porcelain` is empty and it is
already on `main`. `pending/` and `working.md` are ignored by git, so they do not
block the fast-forward; an unpublished dated file does, by design.

It never promotes, never writes `memory/core/`, never force-pushes, never deletes a
ref, never pushes to `main`, and never enables auto-merge. The PR is always a draft.
A rejected push is retried once against a fresh fetch; a second rejection is an
error, not a force. `gh` is used when present; without it the branch is still pushed
and the compare URL is printed so the PR can be opened by hand.

It refuses, exits non-zero, and pushes nothing when:

- `--branch` equals `--base`, `main`, or `master`;
- a pending file fails `dream`'s own line rules (`dream.pending_problem`);
- any file in the allowlist contains a machine path, `/Users/<name>/` or
  `/home/<name>/`.

The first nightly after upgrading may refuse lines containing `/Users/<name>/` or
`/home/<name>/`. The refusal names the bad location as `file:line`; run
`memory-nightly --drop-pending YYYY-MM-DD.md` to remove a rejected pending file
from the branch, or hand-edit the line and publish again.

Another run holding the clone's lock exits 75 and changes nothing.

The branch is a staging area with a human gate:

1. A person reads the draft PR and runs `~/.config/opencode/bin/dream --promote`
   locally, which appends the reviewed lines to the dated files and rebuilds
   `working.md`.
2. They run `~/.config/opencode/bin/memory-nightly` again. That second publish adds
   the archive and drops the promoted `pending/` file from the branch.
3. They review the updated PR diff.
4. They merge it.
5. They delete the `memory/dream` branch. If it still exists with no open PR, the
   next run refuses and prints the delete instruction, because a merged branch would
   otherwise be republished as a stale draft.

Merging before step 2 leaves `pending/` on `main`. CI rejects that: the "no tracked
file is ignored" step exempts `memory/learnings/pending/` only when the head ref is
`memory/dream` **and** the pull request is still a draft, so it fails on `main` and
on every other ref.

Use one machine per branch. A second machine on `memory/dream` overwrites the
first: both fetch and push the same ref for the same UTC date, so the later run
replaces the earlier commit and its open draft. A machine that needs its own
staging queue passes its own branch, for example
`--branch memory/dream-<host>`, and gets one draft PR per host. Delete each branch
after its merge; until a branch is gone, the next run on that machine refuses
because no PR is open.

### Cron

A nightly crontab entry, using the installed path:

```cron
15 3 * * * $HOME/.config/opencode/bin/memory-nightly
```

Pick one scheduler per machine: cron here or the T3 task below, never both.

Either job pushes to the clone's configured `origin`, so it publishes to whatever
remote `./install.cs` cloned — this machine's copy of the repository, not
necessarily the checkout you edit. A fork without write access fails the push.

## Schedule it in T3

T3 has its own scheduler, and that is what this machine uses instead of cron. The job is a T3 scheduled task in the `dotfiles` project: title `Daily dream pass (memory)`, `03:15` local every day, one new thread per run, with a prompt that runs `~/.config/opencode/bin/memory-nightly`, reports the coverage line, the files staged, and the draft PR, and stops if `opencode` is missing rather than hand-writing memory. Dream stages in `memory/learnings/pending/` and the nightly publishes it to the clone's configured `origin` (the remote `install.cs` cloned), so the run ends with a draft PR and a review queue: a person runs `dream --promote`, then `memory-nightly` again to publish the archive and drop `pending/`, before merging.

It lives in T3's userdata, not in git, so it does not travel with this repo and a linked environment needs its own copy. List it from a session in that project, or open the Scheduled tab in T3.

Pick one scheduler per machine. Cron plus a T3 job means two appends into the same dated pending file, and dream's optimistic-concurrency check will start refusing writes. If the scheduler is off for a while, the daily window is `--since 24h`, so the next run only sees the last day; pass `--since` to backfill.

`/dream` is the in-session reminder to use that command later. It is not a step inside T0, T1, or T2 work.
